01Overview

SkyMetropolis is a small city-building game. It runs in a web browser. The player builds a city on a grid of 15 by 15 tiles. A simulation runs in a Web Worker. An AI advisor gives goals and news to the player. A Node server holds the AI key and calls the AI service.

The code uses three different product names. package.json uses “sky-metropolis”. index.html uses “PolyCity AI 3D”. The interface text uses “SkyMetropolis”. Treat these three names as one product.

What the player does

  1. Select a game mode on the start screen. The two modes are AI mayor and sandbox.
  2. Select a building tool in the bottom bar.
  3. Click a tile. The tile receives the selected building.
  4. Read the treasury and the population in the top bar.
  5. Fulfil the goal of the AI advisor. Collect the reward.

What this document covers

This document describes the source code at revision cf8c917. It covers the application layers, the simulation loop, the command system, the game rules, the AI path, the interface, and the build steps. It also records the differences between the code and the labels in the interface.

Scope

This is not a player manual. It does not describe how to play well. It describes how the program is built and where the behaviour comes from. All statements about runtime behaviour come from a reading of the source. The application was not started for this document.

Dependencies

The project has ten runtime dependencies. react and react-dom draw the interface. three, @react-three/fiber, and @react-three/drei draw the 3D city. zustand holds the client state. motion animates the start screen and the handbook. lucide-react supplies the icons. express serves the files. @google/genai calls the model.

03Architecture

The program has three runtime zones. Each zone has one job:

  • The main thread draws the interface and the 3D scene. It also takes the mouse input.
  • The Web Worker runs the simulation. It holds the authority for the game state.
  • The Node server serves the files and calls the AI service. It keeps the API key away from the browser.

One object holds the authority for the game state: the GameKernel. The worker creates one kernel. The kernel owns the grid, the resources, the entities, and the simulation engines. The interface never writes to the kernel. It sends a command. The kernel applies the command and returns a snapshot.

The kernel also owns nineteen core services. It creates each service in the constructor. It registers each service in a global container. It also gives a getter for each service. Most callers use the getters. Only the container uses the names.

Design pattern

The kernel copies the read model into the WorldStateRegistry at the end of each tick. This is a command-query separation (CQRS) pattern. The registry clones the data before it stores the data. A reader cannot change the state of the engine.

04Tick sequence

One tick is the smallest step of the simulation. The worker starts a timer with an interval of 2000 ms. On each interval, the worker calls GameKernel.tick(). The kernel then runs eight steps in a fixed order.

Table 3 — The eight steps of one tick
StepActionCodeResult
1Advance the clockclock.tick()The tick count increases by one. A paused clock stops the tick here.
2Solve the utility graphsolveResourcesAndInfrastructure()Each building becomes a node. Five resources move from producers to consumers.
3Run the enginesscheduler.tick()Economy, population, traffic, and events update by priority and interval.
4Update modifiersmodifiers.update()Timed modifiers lose one tick. Expired modifiers are removed.
5Evaluate rulesruleEngine.evaluate()A true condition applies its effects. The milestone rule pays $5000 at 100 people.
6Evaluate the scenarioscenarioFramework.evaluateStatus()Matching scenario goals become complete. No scenario is active by default.
7Test the AI goalcheckAIGoals()A met goal gets the complete mark. The reward waits for the player.
8Commit the snapshotcaptureSnapshot()The read model receives a clone. The bus emits tick.

Caution

The setFlag method exists, but no caller uses it. The seven default flags are fixed at start. To test the event system, you must change the default value in src/kernel/core/FeatureFlag.ts.

05Player actions and commands

Player input becomes a command object. The command pattern gives three properties at the same time: validation, undo, and a serial form for replay.

Table 5 — Command classes
ClassInputEffectCost
BuildCommandTile x and y, building typeWrites the tile, subtracts the cost, creates an ECS entity, solves the networksCost of the building
DemolishCommandTile x and yClears the tile, destroys the entity5
PolicyToggleCommandPolicy idInverts the policy flag and emits policy_changed0

Each command has three methods: execute, undo, and serialize. The CommandManager keeps an undo stack and a redo stack. A new command clears the redo stack.

Undo and redo

The CommandManager has three lists: an undo stack, a redo stack, and a full history. execute pushes the command to the undo stack and the history. undo pops the command and calls its undo method. A successful undo pushes the command to the redo stack. redo runs execute again.

A BuildCommand keeps the previous tile type. Its undo puts the old type back and returns the cost to the treasury. A DemolishCommand does the opposite. A PolicyToggleCommand only inverts a flag, so its undo is the same operation as its execute.

06Simulation rules

This section gives the formulas as the code implements them. It also gives the differences between the formulas and the labels in the interface.

Economy

The economy engine reads the building list from the ECS. It adds the income of each building. It multiplies the income of shops and factories by the policy multipliers. It subtracts the cost of each active policy. It writes the result to the treasury.

// src/simulation/economy/EconomyEngine.ts
income  = sum(incomeGen × policy multiplier)
expense = sum(costPerDay of each active policy)
money   = money + income − expense
Caution

The engine runs this calculation on every tick. The building descriptions say “per day”. One day is five ticks. The real income is therefore five times the value in the table.

Population and happiness

// src/simulation/population/PopulationEngine.ts
capacity   = houses × 50
growth     = ceil(houses × 1.5 × growth multiplier)
no houses: growth = −5
population = clamp(population + growth, 0, capacity)
citizens   = min(population / 2, 100)   // ECS entities

A citizen entity has a job or no job. A shop gives 5 jobs. A factory gives 15 jobs. A citizen with a job has work factor 90. A citizen without a job has work factor 40. The environment factor starts at 70 and each policy changes it. Happiness is the average of the two factors.

Note

The building file contains a popGen value of 5 for a house. The population engine does not read this value. It uses the growth formula above.

Traffic

vehicles    = min(floor(roads / 2), 30)
congestion  = min(100, round(vehicles / roads × 100))

A vehicle moves to a random adjacent road when it reaches its target. If no neighbour exists, it jumps to a random road. The traffic value in the top bar comes from this calculation.

The policy file also contains requirements and an environmental value. The command does not test the requirements. No engine reads the environmental value. Only the income multipliers, the growth multiplier, the cost, and the happiness value affect the game.

Rules

The kernel loads one rule at start. The rule fires one time, when the population reaches 100. It adds $5000, sends a news item, and sends a second news item about an unlocked building. The building is not locked in the code, so the second item is only a message.

07Utility network

Five resources move through the city: power, water, sewage, internet, and transit. The kernel rebuilds the graph on each tick, before the engines run.

Each built tile becomes a node. Two built tiles get an edge when they touch on one side. A factory is a producer. A house and a shop are consumers. A park is a node with no role. A road is not a node at all, because the graph only includes tiles with a building.

Caution

There is no power plant and no water plant in the building list. A factory is the only producer. A city without a factory has zero utility supply, and every house and shop stays unsupplied.

Supply state

The solver writes two flags on each building entity: powerSatisfied and waterSatisfied. No interface panel shows these flags. No economy formula reads them. They are available for a future rule.

Bridge rule

A road on a river tile becomes a bridge. A bridge must touch a road or a bridge, or the command fails. The game selects the orientation with the largest number of connecting neighbours. On a tie, the code returns east-west. The river shape comes from a sine formula with a centre at x = 7.

Note

The same river formula appears in three places: src/kernel/Command.ts (two copies) and components/IsoMap/utils.ts. A change to one copy does not change the others.

08AI advisor

The AI advisor gives the player a goal. A goal has a description, a target type, a target value, and a reward. The target type is population, money, or building count.

The kernel asks for a goal through the AIService interface. The default implementation is GeminiAIService. It sends a POST request to /api/gemini/goal. The server adds the API key, calls the model, and returns JSON that agrees with a fixed schema.

The repository also has an older service at services/geminiService.ts. No file imports it. It creates a model client in browser code and uses the model gemini-2.5-flash. Do not import it. It would put the key in the client bundle.

Endpoints

Table 8 — Server API
EndpointInputOutputError
POST /api/gemini/goalstats, gridGoal JSON: description, targetType, targetValue, buildingType, reward503 without a key; 500 on a model error
POST /api/gemini/newsstats, recentActionNews JSON: text, type, id503 without a key; 500 on a model error

The goal request uses temperature 0.7. The news request uses temperature 1.1. Both requests set the response type to JSON and give a schema, so the model returns structured data and not free text.

Goal life cycle

The kernel holds at most one goal. The life cycle has four states.

The claim operation calls resources.adjust('money', reward). It then sets the goal to null and emits goal_completed. A new request starts immediately. The interface shows a spinner until the new goal arrives.

Fallback

The procedural service has five goals and eight news lines. It also adds a line about the player's most recent action. The fallback makes the game playable without a key, a network, or a model.

09Interface and visuals

The interface is an overlay on a full-screen WebGL canvas. The overlay has four regions. The player can open a settings deck and a handbook modal from the overlay.

Visual controls

The deck changes the look of the city. It sets the time of day, the weather, the season, the overlay, the photo filter, the camera style, and the audio volume. It also triggers a fire disaster and sets sandbox values for the statistics.

These controls are presentation only. They change colours, particles, light, and sound. They do not change a simulation value.

Sound

AdaptiveSoundscapeEngine makes sound with the Web Audio API. It does not load an audio file. It mixes a low hum, a noise band for weather, and a siren for a disaster. A browser blocks audio until the user clicks. The application waits for the first click or touch.

Rendering

IsoMap is a React Three Fiber scene. It uses an orthographic camera and map controls. The tile height comes from a sine function, and a river carves a lower channel. Buildings are procedural meshes. Cars, citizens, smoke, and weather are small systems with their own update loop.

10Build and run

Prerequisites

  • Node.js 20 or later.
  • npm 10 or later.
  • A Gemini API key for the AI advisor. The game works without a key, but it uses the fixed goals.

Start the development server

  1. Open a terminal in the repository root.
  2. Run npm ci to install the exact versions from the lock file.
  3. Export the key: export GEMINI_API_KEY=your_key.
  4. Run npm run dev.
  5. Open http://localhost:3000 in a browser.
Caution — API key

The README tells you to put the key in .env.local. The server reads process.env.GEMINI_API_KEY only. The dev script runs tsx server.ts without an env-file option. Export the variable in the shell to be sure. Do not commit the key.

Commands

Table 10 — npm scripts
CommandActionOutput
npm run devRuns tsx server.ts. The server starts Vite in middleware mode.Live server on port 3000
npm run buildRuns vite build, then bundles the server with esbuild.dist/ and dist/server.cjs
npm startRuns node dist/server.cjs.Server on port 3000

The server reads NODE_ENV. When the value is not production, the server starts Vite and serves the source files. For a production start, set the value first:

npm run build
NODE_ENV=production npm start

There is no test script, no lint script, and no CI workflow in the current tree. A build problem appears first on a developer machine.

12Limits and gaps

This section records the differences between the intent of the code and the behaviour of the code. Each item names the file that causes the item.

Table 12 — Findings
AreaFindingEffect
High Determinism is not complete. The engines use Math.random() in 43 places. The seeded service is created with seed 1337 but no engine uses it. The replay framework cannot reproduce a run. Two runs with the same commands differ.
High The event system is off. simulation_disasters is false, and no code calls setFlag. The event engine, its five news items, and the disaster counter never run.
Medium A second AI service exists at services/geminiService.ts. It creates a model client in browser code and uses model gemini-2.5-flash. No file imports it. Dead code. An import of this file would put the API key in the client bundle and add a second model name.
Medium Two building tables exist: constants.tsx and src/config/buildings.json. The JSON file has utility and job fields. The TypeScript table does not. A cost or name change can go into one table only. The engine and the toolbar then disagree.
Medium Income is applied on each tick, but the labels say “per day”. One day is five ticks. The economy is five times faster than the labels suggest.
Medium No save and load path exists. The worker handles SET_SNAPSHOT, but no caller sends the message. There is no save button. The save migration framework and the replay framework are unused. A page reload loses the city.
Medium The worker fallback covers construction only. try/catch around new Worker cannot catch an error inside the worker. A worker error leaves the interface without snapshots and without a message.
Medium The utility model has no power plant. A factory is the only producer, and roads do not conduct. Houses and shops are unsupplied in a city without industry.
Low syncWithDelta is defined but never called. Every tick sends a full 225-tile snapshot. A larger grid would need the delta path or a smaller message.
Low The river formula appears in three places. The visual river and the build rule can disagree after a change.
Low The bridge tie-break always returns east-west. A north-south bridge on a symmetric tile can get the wrong deck direction.
Low Policy requirements are data only. The toggle command does not test them. A player can enable a policy before the stated minimum.
Low index.html maps React and three to a CDN through an import map. Vite also bundles these packages. Two copies of React can load. The page also needs network access for Tailwind and the CDN.
Low No tests, no lint rules, and no strict mode in tsconfig.json. A type error can stay in the code until a build fails at run time.
Strength

The project has a clear separation between the domain and the interface. The command pattern and the snapshot message give a stable boundary. The kernel has small services with one job each. It is easy to test a service alone, and easy to add a new engine to the scheduler.
